# 小仓鼠桌宠 更新与发布流程

给维护者 / Agent 按此发版。程序启动后检查公开仓的 `latest.json`，
版本更高则弹出本版更新说明，用户确认后下载、覆盖安装、重启。

机制参照 `D:\VSProject\ChromeClick3.0`，但桌宠是 Python + PyInstaller 单文件 exe，
且**用户数据就在安装目录里**，差异见第 6 节，发版时不要照抄 .NET 那套整目录覆盖。

---

## 1. 仓库与凭据

| 项 | 值 |
| --- | --- |
| 仓库 | 单公开仓（源码 + Actions + Release + `latest.json` 都在同一个仓库） |
| 认证 | Actions 自带的 `GITHUB_TOKEN`，**不需要任何 Secret / PAT** |
| 清单地址 | `https://github.com/<owner>/<repo>/releases/latest/download/latest.json` |
| 客户端配置 | exe 旁边的 `update.json` 的 `repo` 字段，填 `owner/repo` |

> `update.json` 的 `repo` 已配置为 `wAwBill/DesktopPet`。留空即跳过更新检查
> （不报错）。发布脚本会把 `-Repo` 参数写进发布包的 `update.json`，保证下载
> 安装的新用户也能自动更新；该文件在 exe 旁边，**改它不需要重新打包 exe**。

客户端检查更新时先走国内代理（`gh-proxy.com`、`ghproxy.net`、`ghfast.top`），
失败再直连 GitHub；本机实测直连 12 秒超时、代理 1.4～3 秒成功。
以后若有自有 Gitee / OSS，把完整 `latest.json` 地址填进 `update.json` 的
`china_manifest_url`，会作为最高优先线路。

---

## 2. 发版前不要动

- 不要改 `config.json` / `pets.json` / `state.json` 里**用户本机**的那份。
  发布脚本会从源码模板重新生成，不会把用户设置传上公开仓。
- 不要改 `update.json` 的 `repo`（除非仓库改名），客户端靠它找更新源。
- 不要把 `state.json` 提交进仓库，已在 `.gitignore` 排除。
- 不要给 Release 资源起中文名（GitHub 会收成 `default.zip`），固定 `DesktopPet.zip`。
- 不要在多个文件里写版本号，唯一来源是根目录 `version.json`。
- 不要把上一版条目留在 `Docs/发布/本版更新说明.txt` 里往下堆。

---

## 3. 版本号

只改仓库根目录 `version.json` 的 `"version"`，语义化三段：

| 改动 | 新版本 |
| --- | --- |
| 修 bug、小改 | `1.0.0` → `1.0.1` |
| 新功能 | `1.0.1` → `1.1.0` |
| 不兼容（配置格式 / 覆盖规则变了） | `2.0.0` |

Git tag 必须是 `v` + 同一组数字：`1.0.1` → `v1.0.1`。
Actions 会校验 tag 与 `version.json` 一致，不一致直接失败。
`git tag -l "v*"` 看已有 tag，**不要复用已成功发布的 tag**。

---

## 4. 发版步骤

当前分支应为 `main`，工作区只包含本版要发布的改动。

### 4.1 改版本、写更新日志并提交

1. 功能改完，本地验证：
   `python pet.py --selftest`、
   `python scripts/verify_boat.py`、`verify_patrol.py`、`verify_geo.py`、`verify_update.py`。
2. 改 `version.json` 的 `version`。
3. **重写 `Docs/发布/本版更新说明.txt`**：3～6 条用户能看懂的本版改动
   （每行一条，建议 `- ` 开头）。它会进 `latest.json` 的 `notes`，
   显示在「发现新版本」确认框里。不要写安装步骤、不要留示例 / TODO。
4. 提交并 `git push origin main`。

不要提交 `__pycache__/`、`生成稿/`、`publish/`、`_dist/`、`state.json`、`.zip`。

### 4.2 打 tag（真正触发打包）

只推 `main` **不会**发版，必须推 tag：

```powershell
git tag vX.Y.Z
git push origin vX.Y.Z
```

### 4.3 等 Actions

打开 `https://github.com/<owner>/<repo>/actions`，workflow 名 **Release**，
约 2～5 分钟（PyInstaller 打包较慢）。步骤应全绿：

1. Setup Python / Install dependencies
2. Verify tag matches version.json
3. Build release package
4. Verify package contents（校验必备文件与 `state.json` 是空模板）
5. Create GitHub Release

### 4.4 验收 Release

本版 Release 里必须有：

- `DesktopPet.zip`（约 34 MB，各版本文件名相同，靠 tag 区分）
- `latest.json`（`version` / `url` 指向该 zip，`notes` 为本版更新日志）

再打开
`https://github.com/<owner>/<repo>/releases/latest/download/latest.json`
确认 `version` 是刚发的号。

### 4.5 告诉用户

- 已装带自动更新版本的程序：重启后应弹出更新，或右键→「检查更新」。
- 更早的版本没有更新器：需手动下载 `DesktopPet.zip`，解压后覆盖程序目录。
- 覆盖安装不会清掉设置；旧 exe 会自动备份到 `%TEMP%\DesktopPet-update\backup\`。
- 浏览器首次下载的 exe 可能被 SmartScreen 拦截：更多信息 → 仍要运行。

### 4.6 发版后清空更新说明

验收通过后**立刻清空** `Docs/发布/本版更新说明.txt`（留空文件），
提交并 `git push origin main`。否则下一版弹窗里会堆着旧条目。
空文件发不了下一版（发布脚本会拒绝），正好强制重写。

## 6. 与 ChromeClick3.0 的三处关键差异

| 项 | ChromeClick3.0 | 小仓鼠桌宠 |
| --- | --- | --- |
| 构建 | `dotnet publish` (.NET 8) | `PyInstaller` (Python 3.12)，CI 用 `windows-latest` |
| 用户数据 | 在 `%LOCALAPPDATA%\ChromeClick\`，安装目录可整目录 `xcopy` | **就在 exe 旁边**，必须白名单覆盖 |
| 覆盖安装 | `apply.cmd` 里 `xcopy /E /Y` 整个目录 | `updater.prepare_payload()` 先挑出白名单文件，`apply.cmd` 只复制这个 payload |

### 覆盖白名单（改这里要同步改 `updater.py`）

| 处理 | 文件 |
| --- | --- |
| 覆盖 | 主 exe、`pet.py`、`boat_fx.py`、`updater.py`、`version.json`、`使用说明.txt`、`README.md`、`assets/*`、`dialogues*.txt` |
| 合并 | `pets.json`（保留用户 `active` 与自定义形象，追加新版新增形象） |
| 保留 | `config.json`（新字段由程序补默认值）、`state.json`、`update.json` |

本机已有 `config.json` / `state.json` / `update.json` 时，它们**不会进入 payload**，
因此 `apply.cmd` 的整目录 xcopy 也不会碰到用户数据。全新安装时才带模板。

## 7. 客户端更新在做什么

1. 启动 8 秒后（可在 `update.json` 调 `start_delay_sec`）后台请求 `latest.json`，
   代理优先、直连兜底；源码运行和 `--selftest` 跳过自动检查。
2. 远端版本更高则弹出「发现新版本」，展示 `notes`，**用户确认后才下载**。
3. 下载 zip，校验路径穿越 / 绝对路径 / 体积 / 条目数，确认含主 exe 与 `pet.py`。
4. 组装 payload（白名单 + `pets.json` 合并），备份旧 exe，生成 `apply.cmd`。
5. 主程序退出，脚本等待 PID 消失后复制 payload 并重启。
6. 检查失败只写 `%TEMP%\DesktopPet-update.log`，不打断使用。

## 8. 失败怎么处理

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 推了 `main` 但没新包 | 没推 tag | 补推 `vX.Y.Z` |
| `Verify tag` 红 | tag 与 `version.json` 不一致 | 改 `version.json` 后重新提交并打新 tag |
| `Build release package` 红 | PyInstaller 依赖缺失 / 脚本编码问题 | 看日志；确认 `requirements.txt` 已装、`.ps1` 保留 UTF-8 BOM |
| `Verify package contents` 红 | zip 缺文件或 `state.json` 带真实数据 | 检查发布脚本是否用了干净模板 |
| `Create GitHub Release` 红，release 已存在 | 同名 tag 发过 | workflow 已用 `--clobber` 覆盖资源；不要对成功发过的版本重打同名 tag |
| 客户端一直不弹更新 | `update.json` 的 `repo` 为空 / 版本没升高 / 代理与直连都失败 | 依次检查这三项；看 `%TEMP%\DesktopPet-update.log` |
| 更新后设置丢了 | 有人改了白名单，把用户数据放进了 payload | 立刻停止发版，对照第 6 节恢复 |

重发**尚未成功**的同一版本：删远程 tag 再推同名 tag（会重跑 workflow）。
已经成功发过的版本：升号，不要覆盖用户已在用的版本。
不要 `git push --force` 到 `main`。
